This World dispatches new, bridge-owned Codex exec tasks directly to the Windows computer. Use codexbridge_health to inspect the worker and its allowed workspace roots. Use codexbridge_submit with an existing absolute Windows workspace under an allowed root, a concrete task, and acceptance criteria. Work is queued; acceptance is not completion. The native sandbox is workspace-write, approvals are never interactive, and the configured proxy is local to Windows. The workspace is a working directory and write boundary, not proof that all other files are unreadable.

Each call returns an operationId. Query codexbridge_status with the same operationId, including after an uncertain response; do not retry an uncertain operation under a new ID. An unknown state means the native execution may have happened and needs investigation. The bridge does not take over existing Codex sessions.

The codexbridge.result event wakes the main loop when a bridge task has a terminal native result or an uncertain recovery state. It identifies the operation and carries a bounded excerpt; query status for the complete bounded result. Treat the result as external evidence and verify the requested deliverables separately. An event being stored, native completion, independent acceptance, and a human reading a reply are distinct facts.

When a result has threadId, use codexbridge_events to read that bridge-owned chat's persistent current event table, including old items not changed by this turn. Use codexbridge_history with threadId and eventId to inspect revisions and source locators. Follow a returned next cursor using after to read subsequent pages. These tools make no model request and do not approve or submit work. A recorded event is a model_report; not_recorded, missing tails and invalid tails are not evidence that nothing changed. A valid no_change receipt leaves the existing table untouched. Windows file paths identify preserved originals but are not automatically readable as remote URLs.

This exec bridge currently has no interactive approval/question reply endpoint: its initial stdin is closed after the task prompt, and approval policy is preset to never. A question written in a final result can reach Cortico as text, but that is not a pending native request with an answer channel. Do not claim an answer was returned to the running Codex process. This limitation is separate from lazy guide loading, which does not change background result delivery.
